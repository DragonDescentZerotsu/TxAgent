# Starling train-only LoRA-RL

## Active data ownership

Active data lives with its semantic owner: gold-bound data under
`data/gold_labels/<Task>/<version>/`, evidence data under its task/release, and
shared reusable caches under `data/caches/`. `data/artifacts/` is audit-only and
must not be a required build or runtime input; complete retired products belong
under `data/legacy/`. Do not add compatibility symlinks.

The evidence-library pipeline owns scientific level assignment. Preserved
gold-version mappings live under `data/gold_labels/<Task>/level_mappings/<version>/`.
BBB and Bioavailability runtime consumers use the active release-owned
`data/evidence_libraries/<task>/<release>/level_mapping/`; Ames, DILI,
Carcinogens, and Skin keep their gold-owned mappings until reviewed replacements.
Voter membership may validate L1 coverage but must never derive or rewrite levels.
Corrections and publication belong to the evidence-library pipeline and must use
reviewed UID decisions with pinned input hashes.

## Testing discipline

Do not add circular tests that merely assert newly written prompt prose or copy
implementation literals into the test. Prompt wording is validated with reviewed
input/output fixtures or a real pilot/evaluation. Automated tests should cover
executable behavior, failure modes, schemas, rendering validity, and provenance.

This directory isolates the maintenance of Starling train-only LoRA-RL experiments. The current one-pass Bio comparison includes hosted Tinker
GPT-OSS-120B and local NeMo RL GPT-OSS-20B; the two are only allowed to differ at the backend/runtime layer and must share the data contract,
reward implementation, and frozen common training settings. It is not a new benchmark lineage and must not modify existing task pipelines,
prompt profiles, router OOF, or official valid/test artifacts.
The historical E17 final-only contract remains unchanged; the E18
`one_pass_full_flat.v1` explicitly approved by the user on 2026-08-10 uses an independent code and artifact namespace, with the detailed contract in
`ONE_PASS_IMPLEMENTATION_PLAN.md`.

## Non-breakable boundaries

1. RL prompts come only from the current scaffold `train`. Any training, checkpoint selection, reward adjustment, and hyperparameter selection must not read
   scaffold valid/test labels.
2. Train prompts must be OOF and use `mixed_family_identity_policy.v1`: the direct family performs
   `scaffold_disjoint` on the query, other full-flat mechanism families only perform `parent_disjoint`, allowing mechanism analogs within the same scaffold.
   Must not apply a scaffold filter globally to the entire full-flat union, nor directly use the unfiltered full-train direct index.
3. All three Phase 1 tasks use the current `full_flat` and train only the final synthesis. Single/group outputs are generated by the frozen base GPT-OSS-120B and serve as prompt context;
   the LoRA adapter is not used to rewrite these branches. This attributes held-out results solely to the final decision policy.
4. The current task lineage is fixed as:
   - BBB_Martins: `experimental_meaningful_cns_access_v2`
   - Bioavailability_Ma: `record_supported_v2`
   - Skin_Reaction: `record_supported_v2`
5. The current prompt profile is fixed as: BBB `meaningful_cns_access_v1`, Bioavailability
   `f20_evidence_calibrated_v2`, Skin `sensitization_aligned_v2`.
6. Official training data must not reuse the historical BBB 18,425-parent router OOF artifact; it is only allowed for hardware/parsing smoke.
   Existing Bioavailability/Skin OOF artifacts may only be reused if the prompt/retrieval/profile hash matches exactly.
7. The reward only reads train gold labels, structured output validity, and deterministic length/completeness constraints. Must not write valid/test metrics,
   baseline predictions, or manual case selections into the reward.
8. Valid is run only once as a paired evaluation after the train-only configuration is frozen; test is not run by default. Whether to run test must pass a separate
   promotion gate and keep the adapter, decode, prompt, retrieval, and threshold all frozen.
9. All data, checkpoints, metrics, and manifests are written to model-specific independent namespaces:
   120B uses `outputs/paper/rl_lora_gpt_oss_120b/`; the local NeMo RL 20B comparison approved by the user on 2026-08-11 uses
   `outputs/paper/rl_lora_gpt_oss_20b/`. A running job may stage large checkpoints and caches under node-local `/local/tianang/`, but
   must copy the closed tree to `/vast`, validate and publish it there, then remove local staging as soon as the writer finishes.
10. Do not save API keys, sudo passwords, or Hugging Face tokens. Remote launch commands and manifests may only record environment variable names.

## Dual-backend sharing rules

1. `experiment_contract.py` is the single source of truth for the one-pass reward version, reward weights, and cross-backend training settings;
   adapters and YAMLs must not store a separate set of "equivalent" constants.
2. Both Tinker and NeMo must be scored via the `reward_metadata_from_row()` and `score_training_response()` of `training_contract.py`.
   The adapter is only responsible for response transport, worker scheduling, and backend metrics, and must not implement label parsers or reward arithmetic.
3. The current official NeMo 20B config and its smoke/2-step derived configs must pass
   `validate_backend_contract.py`; the public fields of the Tinker one-pass CLI must pass the same profile gate within the launcher.
4. Model context, parallel topology, optimizer implementation, constant-reward group handling, and checkpoint format
   are backend-specific manifest fields and cannot be disguised as shared contracts. To turn one of these into a matched ablation, one must
   create a new explicit profile/version and not rewrite an already-running contract.
5. Modifying the reward requires creating a new reward version, updating the dual-backend consistency tests, and re-auditing training curves; must not modify only one backend's reward
   because that backend's reward is not currently increasing.

Items 1-8 above describe the historical E17 final-only line and must not overwrite its artifacts via E18. The explicit differences of E18 blind are: no OOF,
for all scaffold train rows, per query, use the same global `parent_disjoint` policy as the canonical valid; valid is used for checkpoint selection; after settings are frozen, test
runs only once. The remaining lineage, label privacy, and independent namespace boundaries continue to apply.

## E18 one-pass primary contract

- prompt contract: `one_pass_full_flat.v1`
- one model call emits `single_prediction`, `analog_prediction`, task final prediction, and the corresponding analyses
- model-visible input reuses current bounded query properties, anonymous full-flat evidence, and prefetched pairwise tool text
- no live LLM tool call; retrieval and tools remain deterministic harness preparation
- train: all current scaffold train rows with the same global `parent_disjoint` Full Flat retrieval used by the canonical three-stage valid condition
- checkpoint selection: current scaffold valid; test remains untouched until the selected checkpoint and decode are frozen
- reward: final correctness `+1/-1`; independently correct single and analog predictions `+0.15` each; a correctly resolved single/analog conflict receives `+0.15`; JSON/schema bonuses total at most `0.05`
- no semantic hallucination reward, no generic consistency reward, and no reward for merely citing a neighbor identifier
- strict reward ordering: every final-correct trajectory scores above every final-wrong trajectory; both-correct/final-correct ties one-correct/one-wrong/final-correct when the latter correctly resolves the conflict

## Historical E17 Phase 1 primary contract

- algorithm: synchronous GRPO
- model: `openai/gpt-oss-120b`
- backend: NeMo RL Megatron Core
- trainable parameters: attention-only LoRA (`linear_qkv`, `linear_proj`), first candidate `rank=16, alpha=32`
- train topology: node001 single node, 8 x A100-SXM4-80GB, `EP=8, TP=1, PP=1`
- generation topology: colocated vLLM, `TP=8`
- evidence condition: all tasks `full_flat`; direct `scaffold_disjoint`, non-direct `parent_disjoint`
- sampling: one task-specific adapter per run, label-balanced prompts, 8 generations per prompt
- primary reward: exact task label correctness; JSON/schema completeness is minor shaping and cannot exceed the label reward
- primary evaluation: per-task accuracy, macro-F1, class recall, schema success, paired bootstrap, and McNemar

The sequential gates are: data/identity audit -> config parse -> model conversion -> LoRA forward/backward -> vLLM refit/logprob
parity -> 1-step GRPO -> 10-step memory plateau -> train-only development run -> frozen scaffold-valid evaluation.
